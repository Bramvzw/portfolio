    Hoe sooth bepaalt of een test flaky is of kapot

    Bram van Zwolle · 21 november 2026

    Een rode testrun zegt niet waarom hij rood is. Je draait hem opnieuw, hij wordt groen, en je weet nog steeds niet of de test onbetrouwbaar is of dat er echt iets stuk is.

    sooth is een command-line tool die om je bestaande testcommando heen draait en het JUnit-rapport leest dat dat commando schrijft. Dit artikel beschrijft hoe versie 0.3.4 uit die rapporten afleidt of een falende test flaky is, kapot, of kapot sinds een bepaalde commit. Alles hieronder staat ook in de README en in DECISIONS.md van de repository.

    Flaky betekent: allebei gezien

    sooth noemt een test flaky als de waarnemingen minstens één geslaagde en minstens één gefaalde run laten zien. Een test die in elke waargenomen run faalt, is kapot. Die komt in een eigen sectie en nooit in de lijst met flaky tests. Overgeslagen tests tellen niet mee: een skip zegt niets over de uitkomst.

    De reden staat in DECISIONS.md: een kapotte test flaky noemen beschrijft hem verkeerd, en stuurt iemand op zoek naar toeval dat er niet is.

    Dezelfde code, een ander resultaat

    Binnen één run is dat genoeg. Maar de geschiedenis loopt over commits heen, en dan is “veertig keer groen, daarna rood” dubbelzinnig: is de test onbetrouwbaar, of heeft iemand iets stukgemaakt? Daarom legt sooth bij elke waarneming vast op welke code hij draaide: de commit (HEAD in git) en of de werkmap schoon was. Ongecommitte wijzigingen en nieuwe, niet-gevolgde bestanden maken een werkmap vuil, omdat dat code is die de commit niet beschrijft.

    De regel is dan streng:

    • Flaky is een test alleen als hij op één schone commit zowel slaagde als faalde. Dezelfde code met een ander resultaat laat geen andere verklaring over.
    • Waarnemingen op een vuile werkmap tellen mee in de totalen, maar zijn nooit bewijs. Op welke code ze draaiden, is achteraf niet meer vast te stellen.

    Blijft er daardoor niets over om op te bouwen, dan zegt het rapport dat, in plaats van elke fout als nieuw te laten lezen:

    note: all 9423 earlier observations were made on a dirty tree and cannot be
evidence — commit or stash to let sooth prove flakiness

    Voorbeeld uit de README van sooth.

    sooth leest de commit vóór de eerste run, zodat bestanden die de run zelf schrijft niet als wijziging tellen. Zijn eigen map .sooth/ en het rapportbestand dat je met --junit opgeeft, laat hij buiten die controle.

    Elke run is een waarneming

    Elke run met een rapport voegt per test één regel toe aan .sooth/history.jsonl, in de map waar je sooth start. Zo’n regel bevat het tijdstip, de commit, of de werkmap schoon was, waar de run gemaakt werd (ci als de variabele CI gezet is, anders local), bij welke aanroep van sooth hij hoort, de duur als die bekend is, de status en de naam van de test. Die naam is de classname plus de name uit het JUnit-rapport.

    Het bestand is van jou en blijft lokaal: sooth maakt uit zichzelf geen netwerkverbindingen. De eerste keer dat hij .sooth/ aanmaakt in een repository die de map niet negeert, zet hij hem in .git/info/exclude, dat niet wordt gecommit. Met --no-history sla je een run over, en sooth history toont wat er tot nu toe bekend is zonder iets te draaien.

    Eén aanroep van sooth telt als één stuk bewijs. Voor flaky-bewijs uit de geschiedenis moet de test in de ene aanroep geslaagd en in een andere gefaald zijn, op dezelfde schone commit. Wisselende uitkomsten binnen één aanroep met --runs N beoordeelt sooth apart, in die run zelf. De analyse kijkt per test naar de laatste 50 aanroepen waarin hij draaide.

    Sinds welke commit

    Een test die groen was en vanaf een bepaalde commit steeds rood is, noemt sooth uitdrukkelijk niet flaky. Hij meldt failing since <commit>: een verwijzing naar een regressie, met de commit waar je kunt beginnen (git show <commit>). Daarvoor moet de rode reeks minstens twee aanroepen beslaan en op een schone commit beginnen.

    Was een test nog nooit groen, dan wijst sooth geen commit aan. Hij meldt never seen passing, omdat hij alleen weet waar hij voor het eerst keek. Een bewezen flaky test die sinds een commit in drie of meer aanroepen steeds faalt, houdt zijn label, maar krijgt erbij dat hij sindsdien elke run faalde. Ook een flaky test kan echt kapotgaan.

    Zo ziet dat eruit in een echte run van sooth 0.3.4 op een klein PHPUnit-project, met één test die willekeurig faalt en één test die commit 9cc8049 stukmaakte:

    2 failures — 1 known flake, 1 regression
  ▼ Tests.MailTest::test_receipt_subject — failing since 9cc8049 (the last 5 observed runs)
  ~ Tests.OrderTest::test_ships — known flake (3 of 8 in history, 38%)

    Uit de demo op de case study van sooth.

    Waarom niet gewoon tien keer draaien

    De gebruikelijke manier om een flaky test te vinden is de suite een aantal keer achter elkaar draaien. sooth kan dat ook, met --runs N, maar het is niet de hoofdroute. DECISIONS.md geeft de reden: bewijs via herhaalde runs kost N keer de duur van de suite, dus een suite van vijf minuten kost vijftig minuten. Teams draaien hun tests al vele keren per dag; die waarnemingen bestaan al, sooth hoeft ze alleen te bewaren.

    Herhalen bewijst ook minder dan het lijkt. Een flaky test die in een fractie p van de runs faalt, overleeft N runs met kans (1−p)N. Volgens de tabel in de README vangen vijf runs met 90% zekerheid alleen een test die vaker dan ongeveer 37% van de keren faalt.

    Voor een rode run die je nu wilt begrijpen is er --verify: sooth draait dan alleen de gefaalde tests nog twee keer, wat seconden kost in plaats van de hele suite. Elke fout krijgt dan real (faalde bij elke herhaling), flaky or order-dependent (slaagde bij herhaling, los van de rest), failed differently (faalde met een andere fout dan in de suite) of unverified (de herhaling heeft hem niet gedraaid). Die herhalingen komen niet in de geschiedenis: een test die los van de rest slaagt, zou anders flaky-bewijs opleveren uit een situatie die een gewone run nooit ziet.

    Testrapporten uit CI kunnen er ook bij, met sooth import --env ci --commit <sha> report.xml. CI werkt vanuit een schone checkout, dus juist die waarnemingen kunnen iets bewijzen.

    Exitcodes

    Alles hierboven is uitleg; aan de uitkomst van de run verandert het niets. sooth eindigt met:

    • 0 als de testrunner én zijn rapport het erover eens zijn dat alles slaagde;
    • 1 als de suite faalde;
    • 2 als sooth zelf faalde, of gestopt werd voordat alle runs klaar waren.

    Zo kan CI een rode suite onderscheiden van een kapotte aanroep. Geeft de runner 0 terwijl zijn rapport fouten bevat, dan eindigt sooth met 1 en meldt hij dat. De redenering in DECISIONS.md: “1 failed” tonen en toch met 0 eindigen zou twee waarheden tegelijk zijn, en CI leest exitcodes, geen waarschuwingen.

    Een bekende flaky test maakt een rode run dus niet groen. Voor tests waarvan je dat wel wilt, is er een gecommit bestand .sooth-quarantine met één test per regel, samen met de vlag --fail-on-flaky. De run eindigt dan alleen met 0 als élke fout op die lijst staat.

    Zelf proberen

    sooth is er als kant-en-klare binary voor macOS en Linux en via cargo install sooth. Er zijn presets voor pytest, PHPUnit (ook Pest en php artisan test), Jest (met het pakket jest-junit) en Go (via gotestsum); elke andere runner werkt via --junit met het JUnit-rapport dat hij schrijft. De broncode staat op GitHub, en meer over het project staat in de case study.
